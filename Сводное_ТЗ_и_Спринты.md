## 1. Введение и цели

Документ объединяет финальное ТЗ v1.0, ТЗ v3.0, анализ пробелов и дизайн-макеты в единый план реализации. Назначение — дать команде разработки чёткий пошаговый маршрут от первого коммита до релизной сборки. Все спринты выверены так, чтобы каждый следующий опирался на готовую базу предыдущего и закрывал максимум реальных бизнес-сценариев из ТЗ заказчика.

### 1.1 Что мы строим

Мобильное приложение iOS/Android для управления ремонтными и строительными проектами. Приложение даёт прозрачность по срокам, финансам и качеству работ всем участникам — заказчику, бригадиру, мастеру, представителю — без лишних звонков и сообщений.

### 1.2 Ключевые цифры проекта

| Параметр | Значение |
|---|---|
| Общий срок разработки | 18 рабочих дней |
| Бекенд-спринты | 5 спринтов (10 дней) |
| Flutter-спринты | 4 спринта (8 дней) |
| Длина спринта | 2–3 дня |
| Уникальных экранов в дизайне | ~180 (6 кластеров) |
| Системных ролей | 4 (заказчик / представитель / бригадир / мастер) + admin |
| RBAC doamin-actions | 16 в начальной матрице ТЗ §1.5; в v1.1 фактически **31 action** (детализация `approval.list`, `approval.request`, `approval.decide`, `finance.payment.create/confirm/dispute/resolve`, `finance.budget.view`, `material.finalize`, `selfpurchase.create/confirm`, `step.photo.upload`, `note.manage`, `question.manage`, `methodology.read/edit`, `tools.issue/return`, …) — см. `libs/rbac/src/rbac.types.ts`. Расширение не противоречит §1.5, уточняет гранулярность. |
| Доменных модулей | 16 в начальной декомпозиции; в v1.1 backend-модулей NestJS **20** (auth, users, projects, stages, templates, files, feed, steps, notes, questions, approvals, methodology, idempotency, payments, materials, selfpurchases, tools, health + admin/chat/documents — в S5). |
| Платформы | iOS 14+, Android 7.0+ (API 24) |

### 1.3 Дисциплина спринтов

- Спринт всегда заканчивается работающим инкрементом (можно продемонстрировать).
- Каждая задача спринта связана с конкретным разделом исходного ТЗ и/или экраном дизайна.
- В конце каждого спринта — короткое демо, прогон чек-листа Definition of Done, обновление API-документации (OpenAPI).
- Бекенд и мобильное приложение разрабатываются строго последовательно: к началу мобильных спринтов API стабилизирован.
- Контракт API фиксируется в OpenAPI-схеме сразу после первого спринта — это позволит мобильной команде начать с генерации DTO/клиентов.

## 3. Технологический стек и архитектура

Стек подобран под параметры: высокий темп разработки (18 дней), сложная доменная логика, real-time чаты, push-уведомления, файлы с долгим хранением, гибкая RBAC-матрица, потенциал к росту нагрузки и миграции на масштаб.

### 3.1 Бекенд

| Слой | Технология | Обоснование |
|---|---|---|
| Язык / Фреймворк | Node.js 20 + NestJS 10 (TypeScript) | Зрелый DI-фреймворк, нативные WebSocket-гейтвеи, валидация class-validator, готовые модули CQRS, очереди, расписание. |
| ORM / БД | Prisma 5 + PostgreSQL 16 | Типобезопасные модели, прозрачные миграции, JSONB для прав/настроек, FTS для методички. |
| Real-time | Socket.IO (через @nestjs/websockets) + Redis adapter | Готовые комнаты для чатов проекта/этапа/личных, доставка, переподключения, горизонтальное масштабирование. |
| Кеш / очереди | Redis 7 + BullMQ | Очереди push, генерации PDF и ZIP, расчёта светофора, лимиты SMS. |
| Файлы | MinIO (S3-совместимое) + presigned URLs + sharp (thumbnails) | Долгое хранение (10+ лет), lifecycle-политики, превью, безопасная отдача. |

| Push | Firebase Cloud Messaging (Android + iOS через APNs) | Кросс-платформенно, бесплатно, поддержка topic/condition, deep-links. |
| Поиск | PostgreSQL FTS (русская морфология, pg_trgm + tsvector) | Достаточно для методички/чатов/материалов; миграция на Meilisearch — следующая итерация. **Имплементация (v1.1):** `to_tsvector('russian', title‖body)` вычисляется налету в `$queryRaw` (не сохранённая GENERATED-колонка — `prisma migrate deploy` её не применяет без shadow DB). trigram-индекс на `title` живёт для fallback по опечаткам. | CI/CD | GitHub Actions / GitLab CI → Docker → Compose / k3s | Сборка, миграции, деплой за один пайплайн. |

### 3.3 Архитектура высокого уровня

Бекенд — модульный монолит на NestJS с чёткой границей доменов (DDD-light). Это упрощает развёртывание на старте и оставляет дверь открытой для выноса доменов в микросервисы (chat, files) при росте нагрузки.

- Domain modules: auth, users, roles, projects, stages, steps, approvals, materials, tools, finance, chat, documents, feed, notifications, templates, methodology, admin.
- Поперечные слои: rbac (политики прав), audit (event log в ленту), files (S3-обёртка), realtime (gateway), notifications (FCM + email future).
- Лента событий — централизованная outbox-таблица; все доменные изменения публикуют события, лента подписана и пишет читаемые записи.
- RBAC — комбинация (роль_в_системе × участие_в_сущности × права_представителя). Решение в отдельном сервисе AccessGuard, оборачивающий каждую API-команду.
- Flutter — Clean Architecture: presentation (виджеты) / application (riverpod-провайдеры, usecases) / domain (модели + интерфейсы) / data (DTO, dio-клиенты, drift-репозитории).

## 5. Что мы дополнительно учли (вне явного ТЗ)

Финальное ТЗ закрывает большинство граничных случаев из gaps-анализа. Ниже — пункты, которые мы добавили инициативно: они не противоречат заказчику, но критичны для прод-стабильности.

### 5.1 Безопасность и приватность

- Хранение паролей: bcrypt (cost 12). Никаких plain/MD5.
- Refresh-токены ротируются и привязаны к устройству (deviceId + ip-fingerprint).
- Rate limiting: 5 попыток входа / 5 минут / IP+phone. После — блок 5 минут.
- **Idempotency-Key** для операций с финансовыми/бюджетными последствиями — защита от дубля при потере связи. Реальный (v1.1) перечень `@Idempotent()`-endpoints:
  - `POST /projects/:projectId/payments` (advance);
  - `POST /payments/:id/distribute` (распределение на мастера);
  - `POST /payments/:id/confirm` (двустороннее подтверждение);
  - `POST /materials/:id/finalize` (фиксация суммы купленного → бюджет);
  - `POST /projects/:projectId/selfpurchases` (самозакуп → бюджет при approve).
  Хранение: модель `IdempotencyRecord` (key, userId, endpoint, requestHash, response, statusCode, expiresAt) с TTL 24 ч. Дубль с тем же ключом и телом → сохранённый ответ; с отличающимся телом → `409 idempotency.request_mismatch`.
- Подписанные URL для скачивания файлов (TTL 5 минут), запрет прямого доступа к S3.
- Защита от энумерации телефонов: единый ответ при «номер не зарегистрирован/неверный пароль» в восстановлении.

### 5.2 Производительность и UX

- Светофор и прогресс — материализованные представления: пересчёт по триггеру при изменении шага/паузы/дедлайна, не при каждом GET.
- Фото — компрессия на клиенте до 1920px / 80% качества + EXIF-zero (защита геолокации).
- Превью документов: PDF — первая страница как PNG (генерация в очереди); офисные форматы — иконка + название + размер.
- Курсорная пагинация (cursor based) для лент, чатов, согласований — стабильнее offset при активной записи.
- ETag / If-None-Match на «справочные» запросы (методичка, шаблоны, FAQ) для оффлайн-кеша.

### 5.3 Real-time и оффлайн

- WebSocket-комнаты: `project:{id}`, `stage:{id}`, `chat:{id}`, `user:{id}` — точная фильтрация рассылки.
- Heartbeat 25 сек, переподключение с экспоненциальной задержкой (1s → 30s).
- Очередь отложенных действий в drift — без сети можно отметить шаг, прикрепить фото, оставить заметку; при восстановлении сети — синхронизация (с предупреждением о конфликтах).

### 5.4 Долгое хранение (10+ лет)

- Архивные проекты переносятся в S3 storage class STANDARD_IA / COLD после 1 года неактивности.
- ZIP-выгрузка архива проекта (фото + документы + лента в PDF) — фоновая задача, ссылка приходит push'ом.
- DB-архив: партиционирование `feed_events` и `chat_messages` по году.

### 5.5 Наблюдаемость и поддержка

- Sentry для бекенда и Flutter — single-source ошибок.
- Бизнес-метрики в Grafana: количество активных проектов, среднее время цикла этапа, % просрочек, доля споров по выплатам.
- Health-check'и для очередей и FCM — вебхук в Telegram-чат разработчиков.

### 5.6 Юридические и продуктовые мелочи

- Согласие на обработку персональных данных при регистрации (152-ФЗ) — обязательный чекбокс, ссылка на политику.
- Версионирование политики и пользовательского соглашения — пересогласие при смене версии.
- Формат сумм — единый Money value-object на бекенде (minor units / int64), форматирование на клиенте.
- Тайм-зоны — все timestamp в UTC; на клиенте конвертация в локальную.
- Локализация дат: всегда ДД.ММ.ГГГГ, время по локали устройства.

### 5.7 Подготовка к Pro-версии и платным фичам (заложить, не реализовывать)

- Сущность Subscription / FeatureFlag заложена в схему БД — фичи помечены тегом `plan: free/pro`.
- Точка интеграции с эквайрингом (CloudPayments / ЮKassa) обозначена как stub-сервис.

### СПРИНТ 1 • 2 ДНЯ • ДНИ 1–2

# Backend Foundation: каркас, Auth, Users, Roles, RBAC

#### Цель

Подготовить инфраструктуру и базовые сервисы, на которых вырастут все доменные модули. К концу спринта приложение умеет: регистрировать пользователя по телефону, логинить, восстанавливать пароль через SMS, переключать активную роль, отдавать профиль и список ролей.

#### Задачи по дням

**День 1 — Инфраструктура**

- Репозиторий, NestJS-monorepo (apps/api, libs/*), Prettier + ESLint + Husky.
- Docker Compose: api, postgres 16, redis 7, minio.
- Конфиг через @nestjs/config + Joi-валидация .env.
- Prisma init, базовая схема, первая миграция.
- OpenAPI (Swagger UI) на `/api/docs`, заглушка эндпоинта `/healthz`.
- CI: lint, build, миграции, тесты — на каждый PR.

**День 2 — Auth + Users + Roles + RBAC + Files**

- Модели: User, UserRole, DeviceToken, Session.
- `POST /auth/register` (phone+pass+name+role) — без SMS, как в финале §1.1.
- `POST /auth/login` (phone+pass) → access (15 мин) + refresh (30 дн).
- `POST /auth/refresh`, `POST /auth/logout`.
- Восстановление пароля через SMS-провайдера: `/auth/recovery/send`, `/verify`, `/reset` (3 попытки → блок 5 мин).
- `GET /me`, `PATCH /me` (имя, фамилия, аватар, язык).
- `POST /me/roles`, `DELETE /me/roles/:role` — добавить/убрать роль (без перелогина).
- `PUT /me/active-role` — переключить активную роль.
- `POST /me/devices` — регистрация FCM-токена.
- Сервис **AccessGuard** + декоратор `@RequireAccess('action', resourceLoader)` + базовая матрица прав 4 ролей × 16 действий из финала §1.5.
- Files-модуль: presigned upload в MinIO, presigned download, ограничение по mime/size, обёртка sharp для thumbnails.

#### Артефакты

- Деплоится `docker compose up` — БД мигрирует, можно зарегистрироваться через Postman.
- OpenAPI v0.1: 12 эндпоинтов auth + me.
- Документ `ARCHITECTURE.md` (структура папок, поток запроса, RBAC).

#### Definition of Done

- Покрытие unit-тестами AuthService и AccessGuard ≥ 70%.
- e2e-тест happy-path: register → login → /me → switch role.
- Линтер 0 ошибок, миграции применяются на чистой БД.

#### Задачи по дням

**День 7 — Финансы и материалы**

## 15. Журнал изменений ТЗ

Документ — живой контракт с заказчиком. Все изменения фиксируются здесь с обоснованием; поломанная обратная совместимость требует согласования.

### v1.1 — 2026-04-21 (актуализация по итогам бекенд-спринтов 1–4)

Бекенд S1–S4 реализован и покрыт тестами (323 unit + 23 e2e, все зелёные на коммите `b0c4800` ветки `dev_v1`). В процессе имплементации зафиксированы уточнения и архитектурные решения, которые вносятся в документ:

1. **API contract exceptions** — ради RESTful-группировки 2 endpoint'а отличаются от ТЗ:
   - ТЗ `POST /stages/from-template/:templateId` → фактически `POST /api/templates/:id/apply`.
   - ТЗ `POST /stages/:id/save-as-template` → фактически `POST /api/templates/from-stage/:stageId`.

   Источник истины — OpenAPI (`/api/docs`); мобильной команде генерировать клиенты отсюда.

2. **RBAC расширение** (§1.5): стартовые 16 actions превратились в **31 гранулярный action** — разделили создание/подтверждение/спор/резолв на отдельные права для точных гвардов. Это не конфликтует с матрицей 4 ролей × 16 действий — гранулярные actions группируются в исходные строки матрицы.

3. **FTS методички** (§3.1): `GENERATED ALWAYS AS ... STORED` tsvector не применяется через `prisma migrate deploy` (silently drops). Реально `to_tsvector('russian', title‖body)` считается налету в `$queryRaw`; trigram-индекс по `title` сохраняется для fallback по опечаткам. См. уточнение в таблице §3.1.

4. **Idempotency-Key** (§5.1): расширили с 3 эндпоинтов до 5 (см. §5.1). Хранилище — модель `IdempotencyRecord` (TTL 24 ч), интерсептор атомарно бронирует ключ и сохраняет ответ.

5. **Новые модели в §6** (без конфликта с концепцией):
   - `IdempotencyRecord` — идемпотентность финансовых операций.
   - `ApprovalAttempt` + `ApprovalAttachment` — ранее подразумевались как «ApprovalEvent[]» / «ApprovalAttachment[]», теперь зафиксированы явно.
   - `PaymentDispute` и `MaterialDispute` — сущность «Dispute» из ТЗ реализована раздельными моделями под каждую доменную сущность.
   - `Budget` — НЕ таблица, а **computed view** через `BudgetCalculator`. Это было подразумеваемо в ТЗ («computed view»), закрепляем.

6. **Новые поля на существующих моделях** (§6 актуализирован):
   - `Project.planApproved`, `Project.requiresPlanApproval` — поддержка gaps §3.2 (блокировка start до согласования плана работ).
   - `Stage.planApproved` — кешируемый флаг той же проверки на уровне этапа.
   - `Approval.requiresReassign` — метка pending approvals для уволенного/заменённого бригадира (gaps §2.4). Решение: **не отменять**, а помечать — заказчик переназначает addressee вручную.
   - `Step.authorId`, `Step.assigneeIds[]` — кто создал (важно для extra_work) и кто назначен исполнителем (только мастера проекта).
   - `Payment.resolvedAmount` — итоговая сумма после резолвции dispute с корректировкой.
   - `SelfPurchase.byRole` + `SelfPurchase.addresseeId` — явно зафиксирована иерархия согласования gaps §4.3.

7. **FSM уточнения**:
   - `Step.status` получил `pending_approval` (для extra_work до одобрения) и `rejected` (при reject extra_work).
   - `MaterialRequest.status` — 8 состояний (draft → open → partially_bought → bought → delivered → disputed → resolved; + cancelled).
   - `ToolIssuance.status` — 4 состояния (issued → confirmed → return_requested → returned). issuedQty инкрементится при issue, декрементится при confirmReturn (двусторонний контроль).

8. **Edge-case поведение** (gaps):
   - **§2.4 Удаление/замена бригадира** — мастера НЕ удаляются, только чистится `stage.foremanIds`; pending approvals с `addresseeId=removed` помечаются `requiresReassign=true`. При удалении мастера — очищаем его userId из `step.assigneeIds[]` всех шагов проекта (чтобы не оставались orphan-ссылки).
   - **§2.5 Правка бюджета после старта** — разрешена только customer-owner / rep.canEditStages, эмит `stage_budget_edit_after_start` с payload `{ oldWork, newWork, oldMaterials, newMaterials, notifyUserIds=foremanIds }` (push в S5 берёт `notifyUserIds`).
   - **§4.2 Overflow распределения аванса** — response содержит `warning: 'exceeds_parent_remaining'`, но операция **не блокируется** (решение заказчика — финальное).
   - **§4.3 Иерархия самозакупа** — явно: foreman → owner подтверждает; master → foreman стадии подтверждает.
   - **§5.1 Общие материалы** — `MaterialRequest.stageId = null` означает «Общие материалы» (читаются в рамках проекта без привязки к этапу).
   - **§5.2 Инструмент на профиле** — `ToolItem.ownerId` = userId бригадира с ролью `contractor`; при создании сервис проверяет наличие активной роли.

9. **FeedEventKind** — расширен до **60 значений** (v1.1). Каждое доменное изменение проходит через `FeedService.emit({ tx })` в той же транзакции, что write-операция.

10. **OpenAPI v0.3.0** — зафиксирован после S4 (96 endpoints). Мобильная команда может генерировать retrofit-клиенты.

### 16.2 Внешние блокировки на 2026-04-29

Эти пункты **не зависят от кода** — реализация в репозитории есть, ждём подключения внешних сервисов.

1. **iOS push-уведомления — ⛔ нет аккаунта Apple Developer Program.**
   - Что готово: модуль `firebase_messaging` инициализирован в `mobile/lib/core/push/`, FCM-токен регистрируется через `POST /me/devices`, бекенд (`apps/api/src/modules/notifications/`) отправляет push через FCM-сервис, foreground-уведомления показываются через `flutter_local_notifications`, deep-links через `go_router` обрабатываются (`mobile/lib/core/routing/deep_link_router.dart`).
   - Чего нет: APNs key (`.p8`) не загружен в Firebase Console — для его получения нужна Apple Developer Program ($99/год). Без этого реальный push на физический iPhone не доходит. **Android push функционируют полностью.**
   - Что разблокирует: оплата Apple Developer Program → генерация APNs Auth Key в developer.apple.com → загрузка в Firebase Console → ничего в коде менять не нужно. Раздел §13 чек-листа релиза («FCM-сертификаты iOS (APNs key) загружены») — единственный незакрытый пункт по push.
   - Также блокирует подачу в **TestFlight Internal** (см. §13: «Flutter-сборки подписаны, отправлены в TestFlight Internal»). Google Play Internal Testing работает.

2. **Реальная отправка SMS — ⛔ нет договора с провайдером.**
   - Что готово: `apps/api/src/modules/auth/recovery.service.ts` — endpoints `POST /auth/recovery/send|verify|reset`, генерация 6-значного кода, rate-limit (3 попытки → блок 5 мин), хранилище кодов в Redis с TTL 5 мин.
   - Чего нет: интеграция с провайдером (SMSC.ru / SMS Aero / Stream Telecom) — договор не заключён, API-ключи не получены. На dev/staging код логируется в консоль через `logger.info('[SMS-stub] code=… phone=…')`, реальной доставки на телефон нет.
   - Что разблокирует: заключить договор с одним из провайдеров → подключить ключи через `.env` (`SMS_PROVIDER_API_KEY`) → `SmsProvider`-абстракция уже готова под swap (`apps/api/src/modules/auth/sms-provider.interface.ts`), нужен только реальный driver. **Регистрация без SMS работает по финалу ТЗ §1.1** (логин по телефону+пароль без OTP), SMS требуется только для восстановления пароля и SMS-инвайтов.
