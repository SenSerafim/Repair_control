# Контроль ремонта — Роли, функционал и логика подчинения

Документ собран на основе **ТЗ_Контроль_ремонта_финал v1.0** (`ТЗ_Контроль_ремонта_финал (1).docx`) и реализованных модулей `backend/apps/api/src/modules/*` + `mobile/lib/features/*`. Цель — за один заход понять, **кто что делает, что они видят и кто кому подчинён**.

---

## 1. Краткая сводка ролей

В системе **3 системных роли** (хранится в БД: `customer | representative | contractor`), но **4 функциональных позиции** в любом проекте — потому что `contractor` ведёт себя по-разному в зависимости от того, **кто его назначил и куда**.

| Функц. роль | Системная роль | Кто это | Главная задача |
|---|---|---|---|
| **Заказчик** | `customer` | Владелец проекта (физлицо или компания) | Создаёт проект, ставит бюджет/сроки, принимает работы и оплачивает |
| **Представитель** | `representative` | Доверенное лицо заказчика (жена, дизайнер, прораб-консультант) | Выполняет действия заказчика **по выданному списку прав** |
| **Бригадир** | `contractor`, назначенный **в проект целиком** | Главный исполнитель | Ведёт этапы, назначает мастеров, общается с заказчиком, получает и распределяет оплату |
| **Мастер** | `contractor`, назначенный **на конкретный этап** | Узкий специалист | Выполняет шаги чек-листа, фотографирует, задаёт вопросы по своему этапу |

> 📌 **Ключевой нюанс ТЗ §1.3**: один человек = один аккаунт. Тот же «Максим» может быть бригадиром в проекте у Иванова и одновременно мастером в проекте у Петрова. Поведение определяется **назначением в конкретном проекте**, а не глобальной ролью.

Между ролями добавляется ещё **admin** — администратор приложения (наполняет методичку, шаблоны, FAQ, контакты поддержки, юридические PDF, базу знаний). В проектах не участвует.

## 2. Иерархия подчинения (как реально устроено)

```
                          ЗАКАЗЧИК (владелец)
                       │   создаёт проект
                       │   ставит бюджет/сроки
                       ▼
        ┌──────────────┴──────────────┐
        │                             │
        ▼                             ▼
   ПРЕДСТАВИТЕЛЬ                  БРИГАДИР
   (по правам)                    │   ведёт этап(ы)
   действует от                   │   назначает субподрядчиков
   имени заказчика                ▼
                              МАСТЕР
                              выполняет шаги
                              (заказчик его НЕ видит)
```

Принципы из ТЗ:

1. **Заказчик ↔ Бригадир — прямой канал.** Заказчик видит бригадира полностью (имя, контакты), общается напрямую.
2. **Заказчик не контактирует с мастером бригадира.** «Иначе уводят людей на следующий объект» (ТЗ §1.4). Имя/контакты мастера бригадира заказчику **не показываются**. Все фото и результаты мастера приходят заказчику **как от бригадира**.
3. **Исключение из п.2**: если заказчик сам назначил мастера на этап (минуя бригадира) — он его видит и контактирует напрямую.
4. **Представитель = «второй заказчик» с ограничениями.** Не может создавать проекты, не может архивировать. Всё остальное — по чекбоксам прав, выданным заказчиком.
5. **Бригадир тоже может нанять представителя** (по этапам, на которые он назначен) — для надзора за своими мастерами. Видимость аналогичная.
6. **Сам себя бригадиром назначить нельзя.** Если заказчик ведёт работы сам — этапы остаются без бригадира, заказчик выполняет шаги (ТЗ §1.5).

## 3. Общий функционал (доступен ВСЕМ ролям)

Эти разделы есть у каждого пользователя независимо от роли. Различается только **что внутри видно/можно**.

| Раздел | Кнопка / экран | Что доступно всем |
|---|---|---|
| **Профиль** | `profile/` | Имя, телефон, фото, мои роли (переключение без перелогина), языковые настройки (RU/EN), настройки уведомлений, помощь, FAQ, политика/оферта, обратная связь |
| **Главный экран** «Мои объекты» | `projects/` | Список проектов **в текущей роли**, светофор (🟢🟡🔴🔵), прогресс-бар, % выполнения, фильтр-чипы, кнопка обратной связи (→ Telegram) |
| **Просмотр проекта (консоль)** | `projects/console` | Картинка дома (геймификация), даты, бюджет (видимость по правам), мини-карточки этапов, навигационная сетка |
| **Команда** | `team/` | Список участников проекта с их ролями. Но **видимость зависит от позиции** (см. §8) |
| **Чаты** | `chat/` | Чат проекта, чат(ы) этапа, личные чаты, поиск, пересылка, фото/видео. Уровень чата = уровень иерархии (см. §8) |
| **Документы** | `documents/` | PDF/Excel/Word/JPG. Просмотр встроенный. Фильтры по этапу, категории, дате |
| **Лента событий** | `feed/` | Неизменяемый журнал. Фильтры. Экспорт в PDF (то, что на экране). Архив фото — ZIP |
| **Заметки** | `notes/` | «Мои» (личные) + «Мне» (адресованные другими) |
| **База знаний / Методичка** | `knowledge_base/`, `methodology/` | Чтение статей, видео, поиск (FTS, русская морфология). Наполняет администратор |
| **Уведомления** | `notifications/` | Лента push-уведомлений, deep-link в нужный экран. Критичные (просрочка, спор, дедлайн) — **отключить нельзя** |
| **Помощь** | `support_contacts/` | Контакты поддержки (Telegram/телефон), FAQ |
| **Юридические документы** | `legal_publications/` | Политика, оферта — открываются через внешний браузер (ETag-кеш на стороне моба) |

Общие требования UI (ТЗ §17): автозаглавная буква в названиях, формат сумм `55 550 ₽`, формат дат `ДД.ММ.ГГГГ`, обязательное «Вы уверены?» при деструктиве, оффлайн-режим (drift-очередь синхронизируется при подключении).

## 4. Специфический функционал — ЗАКАЗЧИК

> Главный экран показывает: **проекты, которые я создал (я — владелец)**.

### Что делает только заказчик
- **Создаёт проект** (3-step wizard). Только владелец.
- **Устанавливает плановый бюджет** проекта — отдельно «работа» и «материалы».
- **Архивирует/восстанавливает проект.** Это право **никогда** не выдаётся представителю (ТЗ + RBAC `canArchive: never`).
- **Назначает бригадира в проект целиком** или мастера на конкретный этап.
- **Принимает или отклоняет этап** (статус `На проверке → Завершён | В работе`).
- **Создаёт выплату бригадиру** (аванс, окончательная). Только заказчик инициирует деньги «сверху».
- **Одобряет/отклоняет доп. работу** бригадира — только после одобрения сумма попадает в бюджет.
- **Одобряет/отклоняет запросы на согласование** от бригадира (план этапа, шаг, доп. работа, сдвиг дедлайна, приёмка этапа).
- **Подтверждает самозакуп бригадира** (если самозакуп мастера — подтверждает бригадир, заказчику приходит «через бригадира»).
- **Подтверждает изменение дедлайна этапа** (предлагает бригадир — заказчик подтверждает).
- **Управляет представителями**: добавляет, выдаёт права-галочки, удаляет.
- **Управляет уведомлениями**: критичные отключить нельзя, остальные по типам.
- **Видит ВСЁ**: полный бюджет, всех бригадиров, все этапы, всю ленту, все согласования.

### Что заказчик НЕ видит / НЕ делает
- **НЕ видит** мастеров бригадира (имя, контакты скрыты). Чат этапа бригадира с мастерами — тоже не видит, **если бригадир сам не открыл доступ**.
- **НЕ ведёт инструмент** (это внутренняя кухня бригадира).
- **НЕ запускает и не ставит на паузу этап** — только бригадир.
- **НЕ выполняет шаги чек-листа.** Только может добавлять подшаги-задачи (бригадиру/мастеру приходит уведомление).
- **НЕ отправляет работы на согласование** (он сам адресат согласований).

## 5. Специфический функционал — ПРЕДСТАВИТЕЛЬ

> Главный экран показывает: **проекты, в которые меня добавил заказчик**. Если ни одного — заглушка «Вас ещё не добавили…».

Представитель — это «заказчик с галочками». Все его действия конфигурируются через `RepresentativeRights` (см. `backend/libs/rbac/src/rbac.types.ts`).

### Доступные права (выдаются по чекбоксу заказчиком)
| Право | Что разрешает |
|---|---|
| `canEditStages` | Создавать/редактировать этапы |
| `canCreateStages` | Создавать этапы **без согласования** (как заказчик); в ленте actor_role=representative |
| `canApprove` | Одобрять/отклонять согласования вместо заказчика |
| `canSeeBudget` | Видеть полный бюджет проекта (иначе видит 0 или скрыто) |
| `canCreatePayments` | Создавать выплаты бригадирам |
| `canManageMaterials` | Создавать/обрабатывать заявки на материалы |
| `canManageTools` | Управлять инструментом (если применимо для роли «представитель бригадира») |
| `canInviteMembers` | Приглашать новых участников в проект |
| `canAddRepresentative` | Добавлять других представителей |
| `canManageTeam` | Удалять участников из команды |
| **`canArchive`** | **Заблокировано в типе (`never`).** Архивирование — только заказчик. |

### Жёсткие ограничения (ТЗ §1.5)
- **Не может создать проект.**
- **Не может архивировать проект.**
- **Не может назначить субподрядчика на этап** (это право бригадира, не заказчика).
- **Не может выполнить шаг чек-листа** (это поле подрядчика).
- **Не может управлять инструментом** (если это представитель заказчика; представитель бригадира — может).

### Сценарий
Жена-дизайнер: `canApprove + canManageMaterials = true`, бюджет видеть не нужно → `canSeeBudget = false`. Она одобряет согласования по плитке, заказывает материалы, но цифры не видит.

## 6. Специфический функционал — БРИГАДИР

> Главный экран показывает: **проекты, куда меня добавили исполнителем целиком**.

Бригадир — это `contractor`, назначенный заказчиком **в проект целиком** (через `Membership.role = 'foreman'`).

### Только бригадир может
- **Запускать / ставить на паузу / возобновлять этап.** Причина паузы — обязательно (4 варианта + «другое + текст»).
- **Отправлять этап на проверку** заказчику (только когда все шаги завершены).
- **Создавать чек-лист этапа**: основные шаги + доп. работы (с ценой).
- **Назначать мастеров на свои этапы** (субподрядчиков). Мастера в свою очередь работают только в рамках этапа.
- **Управлять инструментом**: список привязан к профилю бригадира (между проектами переезжает). Выдача мастеру → подтверждение → возврат → подтверждение.
- **Предлагать сдвиг дедлайна** (заказчик подтверждает).
- **Подтверждать получение выплаты от заказчика** (двустороннее подтверждение).
- **Распределять полученный аванс по мастерам** (`Payment.parentPaymentId` связывает родитель↔дочерние).
- **Обрабатывать самозакуп мастера** — подтверждает или отклоняет до того, как сумма уйдёт заказчику.
- **Нанимать представителя для своих этапов** (как заказчик нанимает представителя, бригадир — для надзора за мастерами).
- **Открывать заказчику доступ к чату с мастерами** (опционально, по желанию).

### Видимость
- Видит **бюджет своих этапов** (не общий бюджет проекта, если заказчик не открыл).
- Видит **выплаты от заказчика и свои выплаты мастерам**.
- Видит **всех своих мастеров** (полностью). НЕ видит мастеров других бригадиров.
- Видит **чат проекта + чаты своих этапов**. НЕ видит чаты этапов других бригадиров.

### Что НЕ может
- Создавать проект.
- Назначать в проект других бригадиров.
- Архивировать.
- Видеть общий бюджет проекта (только своих этапов).

## 7. Специфический функционал — МАСТЕР

> Главный экран показывает: **проекты, в которые меня добавили на конкретный этап**.

Мастер — это `contractor`, назначенный **на отдельный этап** (бригадиром, либо реже — самим заказчиком).

### Что делает
- **Выполняет шаги чек-листа** этапа: отмечает «выполнено», прикрепляет фото (компрессия 1920px/80%, EXIF zero на клиенте).
- **Добавляет подшаги/задачи в своих шагах** (свои — менять может, чужие — нет).
- **Задаёт вопросы** по шагу адресатно (бригадиру, либо заказчику если назначен заказчиком).
- **Отправляет операционные согласования** — фото + текст + адресат. Если назначен бригадиром → согласование идёт **бригадиру**. Если назначен заказчиком → **заказчику**.
- **Создаёт заявку на материалы** (адресат: бригадиру или заказчику, в зависимости от назначения).
- **Делает самозакуп** — чеки + сумма → подтверждение бригадира → отображение у заказчика как «через бригадира».
- **Подтверждает выдачу инструмента** и заявляет о возврате.
- **Подтверждает получение выплаты** от бригадира (либо от заказчика, если назначен заказчиком).

### Видимость / ограничения
- Видит **только свой этап(ы)**. Другие этапы проекта не видит вообще.
- Видит **только своих коллег по этапу** (если назначен бригадиром — видит бригадира и других мастеров этого же этапа).
- **НЕ видит бюджет** проекта или этапа (только свои персональные выплаты в ленте «Получено»).
- **НЕ может** запускать/пауза/завершать этап, принимать работы, создавать выплаты, управлять инструментом или бюджетом.
- В ленте видит **только события своего этапа** и **только разделы, к которым есть доступ** (если нет доступа к бюджету — финансовые события не показываются).

### Граничный случай удаления
Мастера удалили с этапа → доступ к чату закрыт, новых сообщений не получает, в чате остаётся пометка «(удалён из этапа)», история сохраняется для остальных.

## 8. Логика подчинения — где она реально работает

| Где | Как проявляется иерархия |
|---|---|
| **Видимость команды** | Заказчик → видит только бригадиров (и тех мастеров, кого назначил сам). Бригадир → видит только своих мастеров. Мастер → видит свой этап. |
| **Чаты** | Чат проекта = заказчик + бригадиры. Чат этапа = бригадир + его мастера. Заказчик чат этапа **не видит** (опция: бригадир может открыть). |
| **Согласования** | Мастер бригадира НЕ может согласовать напрямую с заказчиком — только через бригадира. Если бригадир тянет — заказчик видит в ленте и может написать в чат, но «прыгнуть» через бригадира **не может** (ТЗ §4.4 граничный случай). |
| **Деньги** | Заказчик → Бригадир (родительская выплата). Бригадир → Мастер (дочерняя выплата с `parentPaymentId`). Заказчик мастера бригадира не оплачивает напрямую. |
| **Самозакуп** | Мастер → подтверждение бригадира → у заказчика отображается «Самозакуп через бригадира». Если самозакуп самого бригадира → подтверждение заказчика напрямую. |
| **Уведомления** | Push идут по уровню иерархии: о шагах мастера → бригадиру, о завершении этапа → заказчику. Каждое содержит «[Проект — Роль] Событие». |
| **Лента событий** | Мастер видит только события своего этапа. Бригадир — события своих этапов + общие. Заказчик — всё. |
| **Представительство** | Представитель действует **от имени того, кто его нанял**: представитель заказчика → действует как заказчик (по правам). Представитель бригадира → действует как бригадир в рамках его этапов. |

## 9. Согласования (Approvals)

**FSM**: `pending → approved | rejected | resubmitted` (resubmit инкрементит `attemptNumber`, ограничений на количество попыток нет).

### 5 типов согласований (`scope`)
| Тип | Кто шлёт | Кому | Что внутри |
|---|---|---|---|
| **plan** (план этапа) | Бригадир | Заказчику | Чек-лист этапа до запуска. Пока не одобрен — кнопка «Старт» этапа серая. |
| **step** (операционное по шагу) | Бригадир или Мастер | Бригадиру (если шлёт мастер) или Заказчику (если шлёт бригадир) | Фото + текст. «Кран слева 20 см или справа 30?» |
| **extra_work** (доп. работа) | Бригадир | Заказчику | Текст + цена. До одобрения **не попадает в бюджет**. |
| **deadline_change** (сдвиг дедлайна) | Бригадир | Заказчику | Новая дата + причина. До одобрения дедлайн не двигается (кроме автосдвига при паузе). |
| **stage_accept** (приёмка этапа) | Бригадир | Заказчику | Доступен только когда все шаги выполнены. Одобрение → этап `Завершён`. Отклонение → этап `В работе` + причина. |

### Правила
- Принцип «всё через бригадира»: заказчик **не может** одобрить согласование мастера, минуя бригадира.
- История попыток сохраняется. На карточке: «Попытка 3».
- Представитель с `canApprove = true` решает за заказчика.
- Уведомление — критичное (отключить нельзя).
- Подсветка: 🔵 синий светофор имеет приоритет над 🟡 жёлтым — синий показывается даже если прогресс отстаёт.

## 10. Бюджет и распределение

### Структура бюджета (ТЗ §3.2, §8)
- Бюджет разделён на 2 ведра: **«работа»** и **«материалы»**. Хранятся отдельно, агрегируются в общий.
- На каждый этап — свой плановый бюджет (работа + материалы).
- Все суммы — int64 копейки (`Money` value object), форматирование `55 550 ₽` только на клиенте.
- Версия 1.0 — **только рубли**. Архитектура не привязана жёстко к ₽ (запас на мультивалютность).

### Виды денежного движения (`Payment.kind`)
| Kind | Источник | Получатель | Когда учитывается в бюджете |
|---|---|---|---|
| `advance` (аванс) | Заказчик | Бригадир | После подтверждения бригадиром |
| `distribution` (распределение) | Бригадир | Мастер | После подтверждения мастером. `parentPaymentId` = id родительского аванса |
| `final` (окончательный расчёт) | Заказчик | Бригадир | После подтверждения |
| `selfpurchase` (самозакуп) | Бригадир (свой) или Мастер (через бригадира) | — (списание) | После одобрения заказчиком, идёт в «материалы» |
| `extra_work` (доп. работа) | — | — | Только после одобрения заказчиком, в «работу» |

### Цепочка распределения
```
Заказчик ──advance──► Бригадир (подтверждает) ──distribution──► Мастер (подтверждает)
                          │
                          └──► в финансовом разделе бригадира блок
                               «Получено от заказчика» = список подтверждённых
```
Из этого блока бригадир создаёт выплаты мастерам. Если сумма превышает остаток — система **предупреждает, но не блокирует** (ТЗ §8.2).

### Расчёт и видимость
- `Потрачено = Σ подтверждённых выплат + самозакуп + материалы` (только after-confirmation).
- `Остаток = бюджет − потрачено`.
- **Доп. работа в бюджет НЕ попадает автоматически** — только после `approval.approve` от заказчика (RBAC + service-проверка).
- **Видимость по ролям**:
  - Заказчик: всё.
  - Представитель: по `canSeeBudget`.
  - Бригадир: бюджет своих этапов + свои выплаты. Общий бюджет проекта — нет (если заказчик не открыл).
  - Мастер: только свои персональные выплаты, никаких сумм по проекту/этапу.

### Защита платежей
- Все `POST /payments*` — `Idempotency-Key` middleware (защита от двойного создания).
- Audit-log + событие в `feed_events` (партиционировано по году, неизменяемо).
- Двустороннее подтверждение: создал → получил → подтвердил. Только подтверждённые попадают в `Потрачено`.

### Споры
Любая сторона может «Оспорить» (с обязательной причиной). Спор закрывает тот, кто открыл. До закрытия — статус `disputed`, в бюджет не попадает.

## 11. Функционал по кнопкам / экранам

Ниже — что делает каждая ключевая «плитка» / кнопка консоли проекта и кому она доступна.

### 11.1 Этапы (`stages/`)
- Список: режимы «плитка» / «список», drag-and-drop сортировка (не влияет на логику).
- Параллельное выполнение (электрика + сантехника одновременно).
- Фильтры: статус, подрядчик, проблемы.
- На карточке этапа: %, дата, плашка статуса, 4 кружка-индикатора (подрядчик / статус / вопросы / сроки), таймер паузы.
- **8 состояний** (computed): `Ожидает / В работе / На паузе / На проверке / Завершён / Отклонён / Просрочен / Late-start` (дата старта прошла, но «Старт» не нажат → жёлтый с 1-го дня, через 3 дня → красный).
- **Только бригадир**: «Старт» / «Пауза» / «Возобновить» / «Отправить на проверку».
- **Только заказчик**: «Принять» / «Отклонить» (приёмка).
- **Создание этапа**: blank или из 8 платформенных шаблонов / своих шаблонов. «Сохранить как шаблон» — кнопка на любом этапе.

### 11.2 Шаги / чек-лист (`steps/`)
- Сортировка drag-and-drop. Тип шага: «Основная» или «Доп. работа» (с ценой).
- Мини-меню шага: задать вопрос / добавить подшаг / прикрепить фото-документ / отправить на согласование.
- Подшаги — добавляют все 4 роли (но мастер не редактирует чужие). При добавлении заказчиком — push бригадиру/мастеру.
- Фото загружается с компрессией 1920px/80% + EXIF zero, через `crypto SHA-256` для dedup.

### 11.3 Согласования (`approvals/`)
См. §9. Отдельная вкладка с табами «Pending / History», scope-чипы для фильтра. ApprovalDetail диспетчит на 5 разных body по `scope`.

### 11.4 Бюджет (`finance/`)
- Total / работа / материалы / поэтапная разбивка с progress-bar.
- Бэдж «overspent» если превышено.
- **Кнопки**:
  - Заказчик: «Создать аванс» (выбор бригадира), «Создать окончательный расчёт».
  - Бригадир: «Распределить» (выбор мастера, сумма; validation по `remainingToDistribute`).
  - Любая сторона: «Оспорить» / «Закрыть спор», «Подтвердить получение».
- Видимость — см. §10.

### 11.5 Материалы (`materials/`)
- 8-status FSM: `requested → bought_partial / bought_full → delivery_pending → delivered → confirmed → disputed → resolved → cancelled`.
- Заявка: позиции (название + кол-во + ед. изм + примечание). Получатель — заказчик или бригадир.
- Заявку создаёт: мастер / бригадир.
- Обработка: «Куплено / Частично / Всё». Дата фиксируется автоматически.
- Спор на любом шаге.

### 11.6 Самозакуп (`selfpurchase/`)
- 3-status FSM: `submitted → approved / rejected`.
- Бригадир: подтверждает заказчик → сумма в «материалы».
- Мастер: подтверждает бригадир → у заказчика «Самозакуп через бригадира».
- Прикрепляются фото чеков + общая сумма.

### 11.7 Инструмент (`tools/`)
- Список инструмента — на уровне профиля бригадира (между проектами переезжает).
- FSM выдачи: `issued → confirmed → return_requested → returned`.
- Фильтры: «Все / Выданные / Возвращённые».
- Заказчик этот раздел **не видит** (внутренняя кухня бригадира).

### 11.8 Команда / Подрядчики (`team/`)
- Список с ролями (заказчик / представитель / бригадир / мастер).
- Add member flow: поиск по телефону → найден / не найден (→ SMS-инвайт) → выбор роли.
- Карточка → права представителя (sheet с 13 чекбоксами DomainAction).
- Видимость — см. §8.

### 11.9 База знаний / Методичка (`knowledge_base/`, `methodology/`)
- Категории + статьи + видео (manual thumbnail).
- FTS с русской морфологией (`pg_trgm`, `tsvector`).
- ETag-кеш на мобильном (304-ответы экономят трафик).
- 3 точки входа: профиль, help, console NavGrid `?moduleSlug=`.
- Наполняет администратор.

### 11.10 Чаты (`chat/`)
- Авто-создание при добавлении: заказчик добавил бригадира → чат проекта; бригадир добавил мастера → чат этапа.
- Личные чаты — любой с любым.
- Web-socket `/chats` (11 событий: message.new/edit/delete, typing, presence…), JWT auth, reconnect 1s→30s.
- Edit window — 15 минут.
- Видимость: см. §8. Бригадир может «открыть» свой чат этапа заказчику (опция).
- Фото/видео, пересылка, долгое нажатие на сообщение.

### 11.11 Документы (`documents/`)
- Категории: акты / сметы / договоры / гарантии / фото / планы / прочие (7 типов).
- Документы этапа автоматически дублируются в «Документы проекта» с тегом этапа.
- Встроенный просмотрщик (PDF/Office/JPG).
- Фильтры по этапу/категории/дате. Скачивание.

### 11.12 Лента (`feed/`)
- Чистый журнал, никто не редактирует.
- Категории: stage / step / approval / payment / material / selfpurchase / tool / member / archive (9 типов; **approval имеет приоритет над stage_** при mapping).
- Фильтры: этап / тип / дата.
- Экспорт PDF (то, что отфильтровано). Фото не вкладываются. Архив фото — отдельно ZIP.

### 11.13 Заметки (`notes/`)
- 2 раздела: «Мои» / «Мне».
- Адресные заметки этапа связаны с этим общим разделом.
- Поиск, сортировка по дате.

### 11.14 Профиль и роли (`profile/`)
- Hero + меню. Edit profile.
- **Мои роли** — переключение без перелогина (как в Telegram). Добавление новой роли — через кнопку.
- Настройки уведомлений (lock-icon у критичных + тултип).
- Язык RU/EN.
- FAQ accordion, права представителя info.
- Обратная связь (Telegram), кнопка на главном экране и в профиле.
- «Мои инструменты» — для бригадира.

### 11.15 Уведомления (`notifications/`)
- FCM (soft-fail init), foreground local notifications.
- Deep-link router: 6 payload-видов → пути go_router.
- In-memory список + unread badge.
- Critical нельзя отключить, остальные — по типу.

### 11.16 Прочее
- **Геймификация**: AppHouseProgress (CustomPainter) — дом заливается снизу вверх по % прогресса, цвет = светофор. На 100% — pulse-анимация + glow.
- **ConnectivityBanner**: глобальная offline-пилюля, OfflineQueue с retry x5.
- **Экспорт проекта**: ZIP-архив всех фото + документов.

## 13. TL;DR одной фразой на каждую роль

- **Заказчик** — владелец денег и решений. Создаёт проект, ставит бюджет, нанимает бригадиров, принимает работы, платит. Видит всё.
- **Представитель** — заместитель заказчика по чекбоксам. Делает то, что галочкой разрешил заказчик. Архивировать — никогда.
- **Бригадир** — главный исполнитель проекта. Ведёт этапы, нанимает мастеров, общается с заказчиком напрямую, получает и распределяет деньги, управляет инструментом.
- **Мастер** — узкий исполнитель этапа. Выполняет шаги, прикрепляет фото, задаёт вопросы, заказывает материалы. Видит только свой этап. Если работает у бригадира — заказчик его в принципе не видит.
