# Проблемы по итогам тестирования (черновик для разбора)

Источник — сессия ручного тестирования заказчика. Документ структурирует найденные дефекты, разворачивает каждый пункт и помечает смежные нюансы, замеченные при сверке с ТЗ/кодом. **Решения зафиксированы** под каждым подразделом блоком «**Решение:**» по итогам обсуждения 2026-05-03.

Легенда:
- **Что наблюдалось** — формулировка тестировщика.
- **Что задумано по ТЗ** — что должно быть согласно `Сводное_ТЗ_и_Спринты.md` / ТЗ v1.0 / v3.0.
- **Подозреваемая зона** — модуль/файл бекенда или фичи Flutter.
- **Открытые вопросы** — что нужно решить продуктово до правки.
- **Связанные риски** — побочные эффекты, регрессии, RBAC-конфликты.
- **Решение:** — финальная договорённость для реализации.

## 0. Общая инфраструктура

### 0.1 Сервер «лагает»
- **Что наблюдалось**: задержки в ответах API, иногда «висит» открытие экранов.
- **Что задумано по ТЗ**: p95 ≤ 300 мс на чтение, ≤ 800 мс на запись (см. CLAUDE.md → Observability).
- **Подозреваемая зона**:
  - `progressCache` пересчёт — должен идти триггером + cron 15 мин, проверить, что нет N+1 на `GET /projects/:id`.
  - Socket.IO Redis adapter — если не настроен, Gateway держит лишние соединения.
  - Возможные тяжёлые JSON-сериализации в `feed` (партиционирование по году могло не примениться на проде).
  - Холодный старт NestJS на поде (если деплой single-instance).
- **Открытые вопросы**:
  - Лаги стабильно или эпизодически?
  - На каких эндпоинтах выражены сильнее всего? Логи Sentry/Grafana собирали?
- **Связанные риски**: до фикса перформанса любые UX-фиксы будут восприниматься как «всё ещё тормозит».
- **Решение:** лаги стабильные, прод на одном инстансе. Делаем диагностику в третьем потоке (после фиксов и архитектуры): включить Prisma query logging, замерить N+1 на горячих эндпоинтах (`GET /projects/:id`, `GET /chats/:id/messages`, `GET /feed`), проверить индексы на `feed_events` (партиции по году), оценить долю времени на сериализацию JSON. Redis adapter Socket.IO пока не нужен (один инстанс). Цель: p95 ≤ 300 мс на чтение.

### 0.2 Уведомления уходят не всем / не везде
- **Что наблюдалось**: «починить уведомления все», в чате не приходит всем участникам, «на вкладку согласования стекало абсолютно всё».
- **Что задумано по ТЗ** (v3 §15.2): шаблоны push для каждого события, deep-link в нужный экран, фильтр по `DeviceToken.platform`.
- **Подозреваемая зона**:
  - `notifications.dispatch` (после S18-рефактора) — проверить, что `chat.message_created` рассылает по комнате `chat:{id}` _и_ кладёт push всем участникам, кто не онлайн в данной комнате.
  - Approvals: при `approval.created/updated` падает ли в `feed` категория `approval_*` и в notifications — для всех релевантных ролей (заказчик/представитель/бригадир).
  - На клиенте `NotificationsController` — фильтр по категориям, не отрезает ли часть событий.
- **Связанные риски**: расхождение между real-time доставкой и push (онлайн получает, оффлайн — нет, или наоборот).
- **Решение:** аудитим fanout. В чате push идёт **всем** участникам, кроме автора (без исключения для тех, кто открыл чат, см. 1.3). В Approvals событие `approval.created/updated` создаёт запись для всех релевантных ролей и шлёт push (см. 6.1). Все категории, которые сейчас фильтрует `NotificationsController`, — должны проходить, ничего «молча» не отрезаем.

## 1. Чат

### 1.1 Убрать прикрепление фото и файлов
- **Что наблюдалось**: «убрать из чата возможность прикреплять фото, файлы — в чате только сообщения».
- **Что задумано по ТЗ**: текущая реализация поддерживает вложения (Documents отдельный модуль).
- **Открытые вопросы**:
  - Это окончательное решение или нужна дискуссия? Прикрепление PDF/чертежей в чате — частый сценарий на стройке.
  - Если убираем, оставляем ли возможность шарить ссылку на документ из раздела «Документы»?
- **Связанные риски**: на сервере остаётся endpoint upload-в-чат — нужно тоже отключить или схема сохранится «на будущее».
- **Решение:** убираем целиком. Скрываем UI кнопок прикрепления; в `MessagesController` блокируем поле `attachments` (валидация — только текст); endpoint upload-в-чат (`POST /chats/:id/attachments` или эквивалент) удаляем; миграция БД схему оставляет (не удаляем колонку `Message.attachments` ради совместимости со старыми сообщениями), но новые записи приходят без вложений. Раздел «Документы проекта» работает отдельно, без изменений.

### 1.2 Убрать «Переслать сообщение»
- **Что наблюдалось**: «убрать кнопку переслать сообщение».
- **Подозреваемая зона**: `ChatConversationScreen` long-press menu (S16).
- **Открытые вопросы**: только UI-кнопку или серверный endpoint forward тоже отрезаем?
- **Решение:** убираем только UI (long-press → пункт «переслать» удаляем). Серверный endpoint оставляем, чтобы при необходимости вернуть фичу не пришлось делать миграцию.

### 1.3 Уведомления о сообщениях не уходят всем
- **Что наблюдалось**: «при отправке сообщений всем уведомление уходило».
- **Что задумано по ТЗ**: каждый участник чата (кроме автора), у кого нет открытой комнаты `chat:{id}`, получает push.
- **Подозреваемая зона**:
  - WS-broadcast и push-fanout могли разойтись: WS работает, push — нет (или наоборот).
  - `DeviceToken` не зарегистрирован у части пользователей (после переустановки приложения).
- **Открытые вопросы**: нужно ли пушить и тем, кто сейчас в чате (большинство мессенджеров — не пушит)?
- **Решение:** push **всем** участникам (кроме автора), вне зависимости от того, открыт ли чат. На фронте — соответствующий локальный nudge (foreground-notification) тоже остаётся. Логика «не пушить если открыта комната» из `notifications.dispatch` для category `chat_message` — убрать.

### 1.4 Карточка собеседника при клике
- **Что наблюдалось**: «при клике в чате на кого-либо выводить краткую карточку сверху: название проекта, роль, номер».
- **Что задумано по ТЗ**: спецификация подобной карточки в дизайне отдельно не зафиксирована.
- **Открытые вопросы**:
  - Карточка где: модальный bottom-sheet, отдельный экран, или sticky-header?
  - Какие действия из карточки: позвонить, написать, открыть профиль участника проекта?
- **Решение:** bottom-sheet (modal). Содержимое: имя+фамилия, аватар, роль в проекте, текущий проект (название), список других общих проектов (clickable, скрол), номер телефона. Действия: «позвонить» (`tel:`), «открыть профиль участника проекта». Кнопки «убрать из команды» в карточке чата нет (это отдельный экран команды, см. 2.1).

### 1.5 Формат сообщений «как в Telegram»
- **Что наблюдалось**: «сообщения все верно располагать надо красиво условно как в телеграмме».
- **Текущее состояние**: `ChatConversationScreen` (S16) — reverse list, бабблы, edit/delete на long-press.
- **Открытые вопросы** (надо проявить детально):
  - Группировка по дню (sticky date)?
  - Аватары слева, имя сверху первого сообщения серии?
  - Цвет своих/чужих, время в углу пузыря?
  - Статусы доставки (одна/две галочки)?
- **Решение:** Telegram-style. Sticky date-разделитель сверху каждого дня; группировка серий сообщений одного автора (аватар + имя только над первой); цвет своих/чужих по дизайн-токенам; время в углу пузыря. Статусы доставки (галочки) — **не делаем в MVP** (требуют read-receipt инфры). Long-press: «копировать», «редактировать» (свои, в окне 15 мин), «удалить» (свои). Без forward.

### 1.6 Один общий чат на проект, без личных
- **Что наблюдалось**: «при создании проекта всегда создаётся только один общий чат, новые участники сразу добавлены, личных чатов нет».
- **Что задумано по ТЗ**: в S16 предусмотрены и project chats, и (потенциально) приватные.
- **Подозреваемая зона**: `ChatService.createProjectChat`, миграция, фабрика чатов при `project.create`. Триггер на `Membership.created` — добавление в чат.
- **Открытые вопросы**:
  - Архивные/закрытые проекты — что с чатом (read-only)?
  - Удаление участника проекта — выкидывать из чата сразу или с задержкой?
  - История сообщений до добавления участника — видна или нет?
  - Полностью убираем endpoint создания приватных чатов или прячем только UI?
- **Решение:** один общий чат на проект, без подтем, без приватных. Создаётся автоматически при `project.create`. Триггер на `Membership.created` — добавление в чат. Триггер на `Membership.removed` — удаление из чата (моментально, доступ к истории теряется сразу). Новый участник **видит всю историю** до момента добавления (Telegram-стиль). Архивный проект — чат становится **read-only**, видим всем, кто был активным участником **на момент архивирования** (удалённые из команды до архивирования — доступ не получают). Endpoint создания приватных чатов скрываем из публичного API (оставляем в коде на случай возврата).

## 3. Профиль → Мои инструменты

### 3.1 Улучшить логику добавления инструмента
- **Что наблюдалось**: «улучшить логику добавления инструментов».
- **Текущее состояние**: S15 закрыл «my tools CRUD».
- **Открытые вопросы** (что именно «улучшить»):
  - Добавление по категориям/шаблонам (быстрый выбор)?
  - Добавление пачкой?
  - Фото инструмента, инвентарный номер, серийник?
  - Дубликаты (если 5 одинаковых перфораторов)?
- **Решение:** форма добавления — 4 поля: фото (опц.), название (обяз.), количество (обяз., по умолчанию 1), серийный номер (опц., свободный текст в `comment`/`serial`). 5 одинаковых перфораторов = **5 отдельных записей** с уникальными серийниками (count=1). Bulk-add с автоинкрементом серийника — не делаем в MVP. Категории/шаблоны — не делаем.

### 3.2 Быстрое добавление в проект из «Моих инструментов»
- **Что наблюдалось**: «в проектах добавить возможность добавлять готовые сразу инструменты из того что пользователь добавил в профиле, чтобы это было легко и быстро, удобно».
- **Текущее состояние**: связи «инструмент → проект» из профиля, по факту, нет — добавление инструмента к проекту делается отдельным экраном.
- **Открытые вопросы**:
  - Чек-лист «выбрать из моих» + кнопка «добавить N инструментов в проект»?
  - При добавлении автоматически создаётся `ToolIssuance` с владельцем = текущий пользователь?
- **Решение:** в проекте на вкладке «Инструменты» CTA «+ из моих инструментов» → bottom-sheet с чек-листом моих инструментов (мульти-выбор) → кнопка «Добавить N в проект». При добавлении создаётся запись `ProjectTool` с `ownerId = currentUser`, инструмент сразу попадает в реестр проекта со статусом «у владельца» (`ToolIssuance` пока не создаётся — он создаётся только при заявке от другого участника, см. 8.1).

## 4. Этапы и шаги

### 4.1 Отчёт о выполненных шагах: переделать в «что/как делал + фото»
- **Что наблюдалось**: «надо изменить, сделать логичным мол что делал, как делал, фото прикрепил. Вопросы убираем отсюда».
- **Что задумано по ТЗ**: текущая реализация (S12) — substep-чеклист + фото-grid + thread с вопросами.
- **Подозреваемая зона**: `StepDetailScreen`, `ExtraWorkSheet`, поле «комментарий» при закрытии шага.
- **Открытые вопросы**:
  - «Вопросы убираем» — это отдельная вкладка/раздел вопросов внутри шага? Или вообще убираем механизм вопросов на уровне шага и переносим в чат?
  - Формат отчёта: одно поле «комментарий» + фото-блок? Или 2 поля (что делал / как делал)?
  - Минимально обязательное поле для закрытия шага: текст? Фото?
- **Решение:** убираем substep-чеклист (или прячем). Экран отчёта о шаге — три блока, **все опциональны**: «Что делал» (textarea), «Как делал» (textarea), «Фото» (multi-upload, превью-grid). Кнопка «Отметить выполненным» активна всегда (даже без полей). **Закрытие шага без текста и фото — допустимо**, никаких обязательных полей. Механизм «Вопросы по шагу» **убираем целиком** (см. 4.1 → 17). Если у мастера/бригадира возникает вопрос — пишет в общий чат проекта (см. 1.6).

### 4.2 Загрузка фото не работает
- **Что наблюдалось**: «почини загрузку фото, тут она не работает».
- **Подозреваемая зона**:
  - Клиентская компрессия `compressImage` (S12).
  - Presigned URL — TTL мог истекать раньше отправки.
  - `EXIF-zero` через crypto SHA-256 — могла быть регрессия.
  - Бекенд — `FilesService` policy, лимиты MIME/размера.
- **Открытые вопросы**:
  - Падает на этапе выбора, компрессии, выгрузки или сохранения метаданных?
  - На каких устройствах воспроизводится (iOS/Android, версия)?
  - Что в логах Sentry?
- **Решение:** в первом потоке. Воспроизвести на dev-сборке с `--debug`, локализовать стадию падения (выбор → компрессия → presigned URL → multipart-upload → метаданные). Проверить TTL presigned URL (поднять до 15 мин при необходимости), policy `FilesService` (MIME `image/jpeg`, лимит ≥10 МБ после компрессии до 1920px/80%), регрессию `EXIF-zero` (SHA-256 хеш для дедупа). Прогнать на iOS и Android. Логи — Sentry breadcrumbs + сервер-side ответы.

### 4.3 Доп.работа / доплата / доработка — согласования сломаны
- **Что наблюдалось**: «доп.согласования на доплату/доработку тоже сделать корректными. Сейчас оно всё непонятно и плохо работает».
- **Что задумано по ТЗ** (§4.3 + Gaps §4.1): доп.работа попадает в бюджет ТОЛЬКО после одобрения заказчиком.
- **Подозреваемая зона**:
  - `ExtraWorkSheet` (S12) — auto-approval на бекенде. Это противоречит ТЗ, если auto-approve срабатывает мимо заказчика.
  - FSM `Approval` для scope `extra_work` — проверить, что состояние `approved` действительно требует action заказчика, а не системного авто-одобрения.
- **Открытые вопросы**:
  - Сейчас auto-approve — это легаси/баг или сознательное решение? Если первое — переделать на полноценный approval.
  - Нужен ли ещё один уровень (мастер → бригадир → заказчик)?
- **Решение:** убираем auto-approval из `ExtraWorkSheet` на бекенде. Цепочка: если инициатор **бригадир** → согласование сразу заказчику; если **мастер** → сначала бригадиру, после approve — заказчику; на каждом этапе reject возвращает заявку инициатору с комментарием. После approval заказчика — `extra_work` отнимает сумму из общего бюджета (см. 5.3, п. «Доп.работа»). Заявка попадает в Approvals Inbox (см. 6.1).

### 4.4 Кнопка «Создать кастомный этап» при создании проекта
- **Что наблюдалось**: «на этапе создания проекта есть раздел с этапами, надо починить, создать кнопку добавить кастомный этап».
- **Текущее состояние**: 3-step wizard (S9) — на шаге этапов, видимо, нет CTA «добавить кастомный».
- **Открытые вопросы**:
  - Кастомный этап = тот же flow, что в S11 «blank» шаблон, но прямо в wizard?
  - Можно ли добавлять несколько кастомных в одном wizard?
- **Решение:** в шаге «этапы» wizard'а — две кнопки: «Из шаблона» (платформенные, см. 4.5) и «+ Кастомный этап». Кастомный — компактная inline-форма: название (обяз.), плановая дата старта (опц.), плановая дата окончания (опц.), бюджет этапа (опц.). Можно добавить **несколько** кастомных и смешивать с шаблонными. Удаление/редактирование добавленных — на месте.

### 4.5 Шаблоны этапов: «нет шаблонов» + смещённая надпись
- **Что наблюдалось**: «при создании этапов при нажатии на кнопку открыть шаблоны этапов вылазит уведомление что шаблонов нет, и надпись сама смещена к левому краю».
- **Что задумано по ТЗ**: в S11 — 8 платформенных шаблонов + пользовательские.
- **Подозреваемая зона**:
  - Платформенные шаблоны — сидинг при `prisma migrate deploy` мог не выполниться на проде.
  - Endpoint `/templates` — проверить фильтр (по типу/видимости).
  - Layout: `EmptyState` ушёл в Align.start вместо center.
- **Связанные риски**: если шаблоны не сидируются — все новые проекты теряют 8 заготовок.
- **Решение:** проверить, что seed 8 платформенных шаблонов реально применился на проде (миграция/seed-скрипт в `prisma/seed.ts`); если нет — добавить в обычный `pnpm prisma migrate deploy && pnpm seed:templates` шаг и прокатить через стандартный деплой (без отдельной команды). Поправить layout `EmptyState` шаблонов (центрирование). Пользовательские шаблоны убираем (см. 4.6) — фильтр endpoint'а упрощается до «только платформенные».

### 4.6 Кнопка «Сохранить как шаблон» — убрать
- **Что наблюдалось**: «не понятно куда сохраняет и сохраняет ли вообще, надо убрать полностью эту кнопку».
- **Открытые вопросы**:
  - Убираем кнопку и серверный endpoint? Или только UI?
  - Бизнес-кейс «свои шаблоны» вообще пока выкидываем из MVP?
- **Решение:** убираем целиком (UI кнопку, sheet `SaveAsTemplateSheet`, endpoint `POST /templates/user`, фичу из роадмапа). Существующие пользовательские шаблоны (если есть в БД) — оставляем как «sealed», скрытыми от выдачи; миграцию с удалением колонок не делаем.

### 4.7 Заметка для всей команды не создаётся, если команды нет
- **Что наблюдалось**: «заметка для всей команды не создаётся (команда не была назначена во время тестирования)».
- **Что задумано по ТЗ**: заметка адресуется участникам — если их 0, должно быть либо доступное состояние «без получателей», либо заглушка с CTA «соберите команду».
- **Подозреваемая зона**: бекенд, видимо, требует minLength массива получателей.
- **Открытые вопросы**:
  - Разрешить создание «в пустоту» (станет видно, когда команда соберётся)?
  - Или жёстко блокировать UI с понятным сообщением «нет команды»?
- **Решение:** разрешаем создать заметку даже без команды («впрок»). На бекенде убрать `minLength` для массива получателей. Заметка сохраняется со scope `team-broadcast`. Когда участник присоединяется к команде — заметка появляется у него в ленте с момента **создания** заметки (исторически), фильтрация — на чтении (показываем все team-broadcast этого проекта). Эту же логику применяем для будущих заметок «для команды».

### 4.8 Назначение бригадира на этап
- **Что наблюдалось**: «открываешь этап написано подрядчик не назначен, но должна появляться кнопка назначить бригадира (у заказчика и представителя)».
- **Текущее состояние**: кнопка/sheet, видимо, не выведены на UI. Бекенд-связи stage↔foreman, скорее всего, есть.
- **Открытые вопросы**:
  - Один бригадир на этап или несколько?
  - Можно назначить любого участника проекта с ролью бригадира или только из «команды этапа»?
  - Уведомление бригадиру о назначении (push + feed)?
- **Решение:** один бригадир на этап. На уровне проекта — может быть **несколько разных бригадиров** (на разных этапах). Назначает **только заказчик и представитель** (если у того есть явное право на назначение). На экране этапа — кнопка «Назначить бригадира» (видна только заказчику/уполномоченному представителю), открывает picker всех участников проекта с `role=foreman`. Бригадир получает push (`stage.foreman_assigned`) + запись в feed. Терминология везде — **«бригадир»**, не «подрядчик» (см. 9 + 10.12).

### 4.9 Drag-and-drop порядка этапов на проде
- **Замеченный нюанс**: фича заявлена в S11 (`drag-and-drop reorder`). Проверить, что она реально активна на тач-устройствах (часто HitTest конфликтует со скроллом).
- **Решение:** в первом потоке — ручная проверка на iOS/Android, фикс HitTest при необходимости (long-press → drag handle). Если регрессия глубокая — отдельный issue.

## 5. Бюджет

### 5.1 «Бюджет не задан», хотя задавался при создании
- **Что наблюдалось**: «при нажатии на кнопку бюджет проекта вылазит экран и надпись бюджет не задан, хотя он был задан на этапе создания проекта».
- **Подозреваемая зона**:
  - 3-step wizard (S9) — поле «бюджет» сохраняется в drafts, но возможно не пишется в `Project.budget` при финальном create.
  - Конверсия Money — где-то теряется при int64↔string.
  - Возможен баг чтения: `BudgetScreen` смотрит не в то поле (например, ищет `BudgetBucket.total` вместо `Project.totalBudget`).
- **Связанные риски**: если бюджет реально не сохранён — пострадали все проекты, созданные после регрессии.
- **Решение:** в первом потоке. Проверить SQL: `SELECT id, totalBudget FROM "Project" ORDER BY createdAt DESC LIMIT 20;`. Если бюджет в БД есть — баг чтения в `BudgetScreen` (читает не из того поля); если нет — баг в wizard (`POST /projects` теряет `budget`). Для пострадавших проектов — миграция-correction (если бюджет известен) или попросить заказчика ввести повторно через новую форму «Изменить бюджет проекта» (см. 5.3, доп.работа).

### 5.2 Не отображается бригадир для определения аванса
- **Что наблюдалось**: «не отображается бригадир для определения ему аванса».
- **Текущее состояние**: `CreateAdvance(foreman picker)` в S14 должен показывать бригадиров проекта.
- **Подозреваемая зона**: фильтр пикера тянет участников с `role=foreman`, но если бригадир ещё не назначен на этапы — может отфильтроваться. Связано с пунктом 4.8.
- **Решение:** picker аванса показывает **всех** участников проекта с `Membership.role=foreman` (без привязки к назначению на этап). Завязка на 4.8 — только в части UI термина «бригадир».

### 5.3 Полная переработка логики бюджета
- **Что наблюдалось**: пересказ заказчика — общий бюджет, при покупках/самокупе/авансе уменьшается, может уйти в минус (расходы > план), бригадиру отображается аванс, он перераспределяет.
- **Что задумано по ТЗ**: `BudgetBucket` (work/materials), payments через `Payment.parentPaymentId` (родитель аванс заказчик→бригадир, дети — бригадир→мастер).
- **Расхождения с тем, что описывает заказчик**:
  - Заказчик НЕ упоминает деление на «работы/материалы» как отдельные бакеты — для него это «общий бюджет минус все расходы».
  - Отрицательный бюджет — допустимый стейт (сейчас, возможно, валидация запрещает).
  - У бригадира — отдельный экран «получено в аванс / распределено / остаток на распределение».
- **Открытые вопросы**:
  - Сохраняем ли разделение на work/materials внутри (для отчёта), показывая заказчику единую цифру?
  - Овердрафт — показываем красным, шлём push заказчику при первом уходе в минус?
  - Доп.работа после approval — увеличивает бюджет автоматически, или это отдельная цифра «доп.бюджет»?
  - Самокуп мастера — вычитается сразу или после подтверждения доставки/чека?
- **Решение:** **сохраняем** разделение work/materials внутри (для отчёта). На UI заказчика — единая цифра «Общий бюджет проекта» сверху + раскладка work/materials ниже. Списания из общего бюджета:
  - **Аванс заказчик→бригадир** — отнимает в момент пометки «переведён».
  - **Распределение бригадиром** (бригадир→мастер) — **НЕ отнимает повторно** (это перераспределение уже выданного аванса).
  - **Покупка материалов** — отнимает в момент подтверждения покупки/чека.
  - **Самокуп мастера** — отнимает **в момент approve заказчика** (не при создании заявки).
  - **Доп.работа** — отнимает после approval (см. 4.3).
  - **Овердрафт допустим**: бюджет может уйти в минус, отображаем красным, push при переходе через 0 — **не делаем**.
  - **Изменение бюджета** — новая фича: только заказчик, отдельная кнопка «Изменить общий бюджет» в финансах с confirm-диалогом и записью в audit. Доп.работа само по себе бюджет не увеличивает.
  - **Аванс несколько раз**: разрешаем последовательные авансы (без жёсткого лимита). Пометку «переведён» ставит **заказчик** (как сейчас), вручную после реального банковского перевода.
  - **Видимость**: бригадир и все участники видят общий бюджет; бригадир дополнительно видит свою «корзину аванса» (получено/распределено/остаток на распределение).
  - **Самокуп — отклонён**: если заказчик отклонил заявку самокупа, **никакие деньги из бюджета не отнимаются**, мастер несёт расходы сам, претензии решаются в чате проекта (формальной механики возмещения в MVP не делаем).
  - **Изменение общего бюджета** (новая фича): отдельная кнопка «Изменить бюджет проекта», доступна **только заказчику**, **без согласования** (заказчик — хозяин бюджета). Запись в audit-log + событие в ленту проекта.

### 5.4 Нет одного «дашборда» бюджета по этапам
- **Замеченный нюанс**: BudgetScreen показывает прогресс-бары по этапам — нужно проверить, что они учитывают и материалы, и самокуп, и аванс, а не только work-bucket.
- **Решение:** прогресс-бары этапов суммируют все источники списаний (work + materials + samokup + extra_work, см. 5.3). Овердрафт по этапу — отдельный бэйдж (≥100% залит красным).

## 6. Согласования (Approvals)

### 6.1 Все согласования стекаются на одну вкладку
- **Что наблюдалось**: «починить уведомления все, чтобы на вкладку согласования стекало абсолютно всё: согласования по этапу, деньгам, материалам и т.д.».
- **Текущее состояние**: `ApprovalsScreen` (S13) — tabs + scope chips, 5 scope (plan/step/extra_work/deadline_change/stage_accept).
- **Подозреваемая зона**:
  - Не все доменные события создают записи в `Approval`. Например, материалы (S15) — там своя FSM 8 статусов, она может НЕ генерить Approval-записи.
  - Самокуп — отдельная FSM (3 статуса), требует approve/reject, но попадает ли в `ApprovalsScreen`?
  - Финансы (диспуты) — `Payment dispute resolve` сейчас идёт через CTA в PaymentDetail, не через approvals.
- **Открытые вопросы**:
  - Что входит в «всё»: материалы, самокуп, инструмент-issuance, диспуты по платежам, передача инструмента?
  - Делать ли единую модель «Approval-Inbox», агрегирующую разные FSM, или расширять существующий `Approval` на новые scope?
- **Решение:** **расширяем `Approval`** на дополнительные scope (а не делаем агрегатор). В Inbox попадает **всё кроме инструментов**. Новые scope:
  - `material_purchase` (закупка материалов): инициатор — бригадир, заявка вида «купить плитку за X». Approve заказчика → сумма **сразу списывается** из общего бюджета. Бригадир покупает фактически и прикрепляет чек к заявке (опционально). Если покупка по факту не состоялась — заказчик корректирует общий бюджет через «Изменить бюджет» (см. 5.3). Reject → ничего не списывается.
  - `self_purchase` (самокуп мастера): инициатор — мастер. Approve заказчика → списание (см. 5.3). Reject → ничего, претензии в чат.
  - `payment_dispute` (диспут по платежу): инициатор — получатель платежа (мастер по выплате от бригадира, бригадир по авансу от заказчика), указывает сумму и причину. Решает заказчик. Approve → корректировка платежа (отметка `disputed/resolved`), без автоизменения бюджета (заказчик может донести через «Изменить бюджет»). Reject → диспут закрывается.
  - `stage_create` (этап, созданный бригадиром, см. 7.4)
  - `budget_change` — **не нужен**: изменение бюджета — прерогатива заказчика без approval (см. 5.3, доуточнение E1). Убираем из списка scope.
  
  Существующие scope (`plan`, `step`, `extra_work`, `deadline_change`, `stage_accept`) остаются. **Инструменты** имеют отдельную FSM (см. 8.1) и в Inbox **не попадают** — у них своя вкладка.
  
  Push на каждое попадание — **отдельный** (без суммирования). DeepLinkRouter расширить под новые scope (см. 10.3).

## 7. Роли и RBAC

### 7.1 Заказчик: «Архивировать проект» не работает
- **Что наблюдалось**: «архивировать проект не работает — может выполнить только заказчик».
- **Что задумано по ТЗ**: archive — право заказчика (и представителя с правом).
- **Подозреваемая зона**:
  - `AccessGuard` для `project.archive` отдаёт 403 даже заказчику (баг политики).
  - На клиенте кнопка не подключена.
- **Связанные риски**: пока не починено — заказчик не может закрыть проект, копится мёртвый список.
- **Решение:** архивирование — **только заказчик** (см. 7.3, право представителя «архивирование» отменяется). В `AccessGuard` для `project.archive` — единая проверка `Membership.systemRole === 'customer'`. Confirm-диалог: «После архивирования проект исчезнет у всех участников, останется только у вас в архиве. Продолжить?». В audit — событие `project.archived` с `actorId`. См. также 9.2.

### 7.2 Остальные роли: «скрыть» / «выйти из команды»
- **Что наблюдалось**: «остальные могут только скрыть или выйти из команды объекта».
- **Текущее состояние**: насколько понимаю, и «скрыть для себя», и «выйти» сейчас реализованы частично/не консистентно.
- **Открытые вопросы**:
  - «Скрыть» = персональный hide (видимость 0 у меня)? Или soft-archive?
  - «Выйти из команды» = self-removal из Membership? Что с историей шагов/одобрений мастера, который вышел?
  - Бригадиру разрешено выйти, если он держит активные авансы/инструменты?
- **Решение:** «Скрыть» = персональный hide в списке проектов (флаг `Membership.hiddenForUser`, не влияет на чат и доступ). «Выйти из команды» = soft-removal (`Membership.removedAt`, доступ к проекту и чату теряется моментально, см. 1.6). Бригадир **может выйти** даже с активными авансами/инструментами — модалка предупреждения «У вас активные обязательства, выход не отзывает их. Заказчик увидит уведомление». Для инструментов — отдельная развилка (см. 8.1, п. ухода бригадира).

### 7.3 Представитель: нет прав, хотя выданы
- **Что наблюдалось**: «создал представителя, добавил в проект, ограничил ему только права на редактирование и архивирование. Но у него нет вообще никаких прав: создавать этапы не может, чаты тоже и т.д.».
- **Что задумано по ТЗ**: `RepresentativeRights` JSONB на Membership; матрица 4 ролей × 16 действий — ТЗ §1.5; 13 `DomainAction` в `RepRightsSheet` (S10).
- **Подозреваемая зона**:
  - `RepRightsSheet` сохраняет права не в той структуре, которую читает `AccessGuard`.
  - `AccessGuard` не учитывает `RepresentativeRights` для scope, который не из 13 явных DomainAction (например, чат/этапы).
  - Возможно, представителю ВСЕГДА не хватает прав, потому что guard сначала проверяет «системную роль = customer», а потом не fallback-ает на rep rights.
- **Открытые вопросы**:
  - Какие именно действия представитель должен мочь делать «по умолчанию» (без отдельного права), а какие — только при явном включении?
  - Должен ли представитель быть полноценным администратором (мини-заказчик), либо узко-ограниченной ролью?
- **Решение:** представитель — **узко-ограниченная роль**. По умолчанию (без явных прав) может **только**: смотреть всё (бюджет, этапы, шаги, документы, ленту, согласования) и **писать в чат**. Любое действие по изменению (создание этапа, согласование, назначение бригадира, аванс, доп.работа) — **только при явном включении** через `RepRightsSheet`. **Архивирование** — никогда (исключаем из списка `DomainAction`, см. 7.1). `AccessGuard` переписать: для роли `representative` сначала проверка по `RepresentativeRights` JSONB, fallback — read-only-доступ к проекту. Все 13 текущих `DomainAction` ревизуем — оставляем только реально-влияющие на запись.

### 7.4 Бригадир: создание этапов через согласование
- **Что наблюдалось**: «бригадир может создавать этапы, но они должны согласовываться с заказчиком (или представителем с правами)». Сейчас, видимо, либо не может, либо создаёт без согласования.
- **Подозреваемая зона**: scope `plan` в Approvals задумывался под план целиком, не под отдельный этап. Нужен либо новый scope `stage_create`, либо расширение `plan`.
- **Открытые вопросы**:
  - Согласование на каждый созданный этап или пакетно (пакет «новых этапов»)?
  - До согласования этап в статусе `draft` (невидим мастеру) или сразу видим, но «pending approval»?
- **Решение:** добавляем scope `stage_create` в Approval (см. 6.1). Бригадир создаёт этап → этап **виден всем** в списке этапов с серой плашкой «Ожидает согласования». **Кнопки шагов заблокированы** (нельзя начать работу) до approve. Согласование — **по каждому этапу отдельно** (не пакетно). Approve уходит заказчику (или представителю с правом). Reject возвращает этап в состояние `rejected` с комментарием, бригадир может пересоздать. **Представитель с правом «создание этапов»** — создаёт этап **без согласования** (право выдано заказчиком), как сам заказчик; в audit/feed — пометка «Иванов И. (представитель)».

### 7.5 Бригадир: назначает мастеров на этапы
- **Что наблюдалось**: «в этапах бригадир может в свою очередь назначить ответственных мастеров за этапы».
- **Текущее состояние**: возможно, такого механизма ещё нет (бригадир может только назначаться сам, или мастера видят все этапы без явного assigned).
- **Открытые вопросы**:
  - Один мастер на этап или несколько?
  - Может ли заказчик переопределить выбор бригадира?
  - Уведомление мастеру при назначении.
- **Решение:** один мастер на этап (по аналогии с одним бригадиром). Назначает **бригадир** (на свой этап) или **заказчик/представитель** (с переопределением, если нужно). Кнопка «Назначить мастера» в карточке этапа, picker — участники проекта с `role=master`. Мастер получает push (`stage.master_assigned`) + запись в feed. Если мастер не назначен — этап ведёт сам бригадир (см. 7.6).

### 7.6 Сдача этапа: цепочка мастер → бригадир → заказчик
- **Что наблюдалось**: «при сдаче этапа мастер всё отмечает, затем бригадиру на согласование, бригадир согласовывает, затем заказчику. Или бригадир сам отмечает шаги, закрывает этап, и тогда сразу всё отправляется заказчику».
- **Текущее состояние**: scope `stage_accept` в Approvals, скорее всего, идёт сразу к заказчику от того, кто завершил.
- **Открытые вопросы**:
  - Двухступенчатый approval — это новая FSM (мастер→бригадир→заказчик), либо два последовательных approval-а одного scope?
  - Если мастера на этапе нет (бригадир сам ведёт) — пропускаем шаг бригадира?
- **Решение:** **две последовательные Approval-записи** одного scope `stage_accept` с разным `actorRole`. Логика:
  - Если на этапе **есть мастер**: мастер закрывает этап → создаётся `Approval#1 (actorRole=foreman)` → бригадир approve/reject → если approve, создаётся `Approval#2 (actorRole=customer)` → заказчик approve/reject → если approve, статус этапа = `done`.
  - Если на этапе **нет мастера** (бригадир сам ведёт): шаг бригадира пропускаем, сразу `Approval#1 (actorRole=customer)`.
  - **Reject бригадира** (ступень мастер→бригадир): этап возвращается в `active`, мастер дорабатывает и пересдаёт (создаётся новый `Approval#1`).
  - **Reject заказчика** (ступень бригадир→заказчик): этап возвращается **бригадиру** (не мастеру), потому что бригадир уже принял работу мастера и несёт ответственность перед заказчиком; бригадир сам разбирается (доделывает или возвращает мастеру неформально через чат), затем повторно отправляет на согласование заказчику.
  - Кнопки приёмки видны строго по `actorRole` текущего активного approval (см. 7.7).

### 7.7 Кнопки «принять/отклонить» доступны не той роли
- **Что наблюдалось**: «убрать кнопки принять работу или отклонить — эти кнопки есть только у заказчика или представителя».
- **Подозреваемая зона**: `ApprovalDetailScreen` показывает CTA по умолчанию всем участникам approval; нужно фильтровать по роли + scope.
- **Решение:** в `ApprovalDetailScreen` CTA «Принять/Отклонить» показываются **только** тому, чья `Membership.role` совпадает с `Approval.actorRole` текущего активного шага. Все остальные видят approval read-only с плашкой «Ждёт согласования {роль}». Мастер: «принять/отклонить» — никогда. Бригадир: «принять/отклонить» — только если активен `Approval#1` его этапа (см. 7.6) или адресный scope (например, `extra_work` от мастера, см. 4.3).

### 7.8 Мастер
- **Что наблюдалось**: раздел в исходном списке начат, но требований не сформулировано.
- **Открытые вопросы (нужно вытащить у заказчика на следующей встрече)**:
  - Какие конкретно сценарии у мастера ломаются?
  - Видит ли мастер только «свои» этапы (assigned) или все этапы проекта?
  - Может ли мастер сам инициировать самокуп/доп.работу или только бригадир?
- **Решение:** во втором потоке — провести аудит UI/UX роли «мастер» **по коду** (без отдельного тестового логина): пройти по всем экранам — профиль, проекты (только те, где `Membership.role=master`), этапы (видит все, работает только в назначенных), шаги (отчёт по 4.1), доп.работа (см. 4.3, цепочка через бригадира), самокуп (мастер инициирует, approve заказчика), инструменты (заявка на получение, см. 8.1), чат, уведомления, согласования (read-only, без CTA, см. 7.7), бюджет (видит общий, см. 5.3). Сверить UI-кнопки с реальными правами в `AccessGuard` и `RBAC`. **Скрыть нерабочие кнопки**, оставить только функциональные. Чек-лист сценариев — собрать после первого прохода.

## 8. Инструменты

### 8.1 Полная переработка логики
- **Что наблюдалось** (пересказ): инструмент создаёт заказчик ИЛИ бригадир. Бригадир/мастер при необходимости получить инструмент создаёт заявку владельцу. Владелец одобряет передачу. На вкладке всегда видно «у кого сейчас находится». При создании владелец = тот, кто добавил.
- **Текущее состояние**: S15 — Tools (my tools CRUD) + ToolIssuance FSM (`issued → confirmed → return_requested → returned`).
- **Расхождения**:
  - Сейчас, видимо, владелец-создатель только заказчик (или это работает только из «my tools» в профиле). Нужно поддержать и бригадира как создателя инструмента в проекте.
  - «Заявка на получение» — отдельный шаг перед `issued`, сейчас FSM начинается с `issued` (т.е. передача уже совершена, нужно лишь подтверждение).
  - Нужен общий «реестр инструментов проекта» с колонкой «у кого сейчас» — UI этого, кажется, нет.
- **Открытые вопросы**:
  - Заявка попадает в общий поток согласований (см. 6.1)?
  - При утере / поломке — отдельный сценарий? Кто компенсирует?
  - История перемещений инструмента — нужна?
  - Если бригадир добавил инструмент в проект, а потом ушёл — что с инструментом?
- **Решение:**
  - **Создание**: каждый создаёт инструмент **только от своего имени** (заказчик не может «добавить инструмент бригадира»). Владелец = создатель.
  - **FSM `ToolIssuance`** (расширяем): `requested → approved → issued → confirmed → return_requested → returned`. Заявку создаёт желающий получить (бригадир/мастер), `approved` — действие владельца. После `approved` владелец фактически передаёт инструмент, получатель отмечает `confirmed`. Возврат — симметрично.
  - **НЕ через Approvals Inbox** (см. 6.1). У инструментов своя вкладка с активными заявками.
  - **Реестр инструментов проекта**: ключевое требование — **все участники проекта видят** список всех инструментов проекта + колонку «у кого сейчас» (`currentHolderId` = последний confirmed получатель, либо владелец). Реестр виден всем, чтобы любой мог понять, к кому обращаться за нужным инструментом. Бэйдж «есть активная заявка» — виден всем (прозрачность); сама заявка с кнопками approve/reject — видна только владельцу и инициатору.
  - **История перемещений** — не нужна (см. 43). Достаточно текущего держателя.
  - **Утеря/поломка** — вне MVP (см. 44).
  - **Уход бригадира** (см. 7.2): при попытке выхода из команды — модалка «У вас N инструментов в проекте. Что с ними?» с радиокнопкой «Передать заказчику» / «Забрать с собой (удалить из проекта)». «Передать» — `ownerId` всех его инструментов меняется на заказчика, текущий держатель сохраняется. «Забрать» — инструменты удаляются из проекта, **активные `ToolIssuance` принудительно завершаются** (`force-return`); если инструмент сейчас у мастера — мастер получает push «Инструмент {name} отозван владельцем» + запись в feed.

## 10. Дополнительно замеченные пункты (от меня)

Эти моменты не упоминались в исходном списке, но напрямую связаны с заявленными проблемами и при правках их желательно поднять одновременно.

### 10.1 Согласованность offline-режима с новыми правилами
- В S17 закрыта `OfflineQueue` для отметки шагов / фото / заметок. Если меняем формат отчёта о шаге (4.1) — очередь надо обновить, иначе оффлайн-операции упадут на сервере при синке.
- **Решение:** обновить схему отложенных операций под новый отчёт (опциональные поля «что/как делал», multi-photo). Бекенд должен принять старые/новые операции (graceful — если поле отсутствует, считаем пустым).

### 10.2 Push при оффлайн-доставке + Idempotency
- Для финансов (`POST /payments*`) есть `Idempotency-Key`. Если ломаем/чиним аванс — проверить, что offline-повтор не порождает двойную выплату.
- **Решение:** при правке логики аванса (5.3) — обязательная регрессионная проверка `Idempotency-Key` (offline-повтор ровно тот же ключ → один payment). Покрыть e2e-тестом.

### 10.3 Лента (Feed) и переход «уведомление → экран»
- В S17 закрыт DeepLinkRouter (6 видов payload). Если добавляются новые approval scope (8.1, 7.4) — нужно расширить router и шаблоны push.
- **Решение:** расширить DeepLinkRouter под новые scope из 6.1 (`material_purchase`, `self_purchase`, `payment_dispute`, `stage_create`, `budget_change`) + под назначение бригадира/мастера на этап (4.8, 7.5) + под инструменты (`tool.requested`, `tool.approved`, `tool.return_requested`, см. 8.1). Шаблоны push обновить в `notifications.dispatch`.

### 10.4 RBAC и право представителя на «архивирование»
- Заказчик дал представителю «право на архивирование», ожидает, что тот сможет архивировать. Если архив — крайне опасное действие, продуктово стоит решить: даём ли это вообще представителю, и если да — нужно ли двойное подтверждение / запись в audit-log с пометкой «выполнено представителем».
- **Решение:** право «архивирование» представителю **не выдаётся ни при каких условиях**. Удалить опцию из `RepRightsSheet` (UI + список `DomainAction`). Архив — эксклюзив заказчика (см. 7.1, 9.2).

### 10.5 Согласование между бригадиром и заказчиком через представителя
- Сценарий: представитель имеет право на согласования, но мастер всё равно отправляет «заказчику». Кому в итоге уходит push: заказчику, представителю, обоим? Если обоим — кто «решает» при расхождении?
- **Решение:** push идёт **обоим** (заказчику и представителю с правом). Approval — единая запись с `actorRole=customer`. Решает **тот, кто первый успел** (approve/reject). После действия второму приходит финальный статус-push «решено N». В audit пишем фактического `actorId`. Если разногласие постфактум — обсуждается в чате, формальная запись остаётся.

### 10.6 Чат: история при переходе участника
- Связано с 1.6: новый член проекта добавляется в чат — нужно решить, видит ли он историю до момента добавления (сейчас это конфигурация на уровне `ChatService.addParticipant`).
- **Решение:** видит **всю историю** до момента добавления (Telegram-стиль). `ChatService.getMessages` без фильтра по `joinedAt`.

### 10.7 Заметки и команда
- Связано с 4.7: заметка может быть «для команды» или «для отдельных людей»? Нужно ли разделить на два сценария?
- **Решение:** упрощаем — все заметки **для всей команды** проекта (`scope=team-broadcast`). Заметки «для отдельных людей» в MVP не делаем; адресная коммуникация — через чат.

### 10.8 Светофор / прогресс при сломанном бюджете
- Если бюджет не загружается (5.1), а светофор завязан на «расход vs бюджет», часть веток состояния может молча падать в дефолт. Стоит проверить `progressCache` на null-safe.
- **Решение:** в `ProgressCalculator` заводим explicit-ветку «бюджет не задан» — светофор считается только по срокам/прогрессу шагов, без бюджетного компонента. Покрыть unit-тестом.

### 10.9 Производительность чата при 1 общем чате на проект
- Связано с 1.6: если все участники сидят в одной ленте, выросший проект (50+ человек) даст эффект «чат N+1». Нужен курсорный пагинатор и backfill.
- **Решение:** проверить, что `GET /chats/:id/messages` курсорный (по `id` или `createdAt`), без N+1 на авторов. Загрузка по 50 сообщений, infinite-scroll вверх. На WS-broadcast — `socket.to('chat:{id}')`, без individual emit.

### 10.10 Тест-данные и сидинг
- Симптомы 4.5 («шаблонов нет») и 5.1 («бюджет не задан») — кандидаты на пропущенный сидинг/миграцию. Стоит проверить, что фронт читает не stale-кеш, а сервер реально возвращает данные (через прямой curl на endpoint).
- **Решение:** после фиксов — прокатить через **обычный деплой** (`pnpm prisma migrate deploy && pnpm seed:templates`). Дополнительной отдельной команды не требуется. Smoke-test после деплоя: `curl /templates` возвращает ≥8 платформенных, `curl /projects/:id` возвращает `totalBudget`.

### 10.11 Уведомления критичных событий и lock-icon
- В S17 заложен `NotificationSettings lock-icon` для критических. Если решаем «убрать чат-уведомления тем, кто в чате» (1.3) — уточнить, что это _не_ относится к критичным (approval, finance, etc.).
- **Решение:** по 1.3 push в чате идёт **всем** (даже тем, у кого открыта комната), так что коллизии с lock-icon нет. Критические события (approval, finance) — продолжают пушить всегда, lock-icon в `NotificationSettings` для них активен.

### 10.12 Согласованность RU-формулировок
- Терминология «бригадир» / «подрядчик» / «foreman» путается между UI и этим списком («подрядчик не назначен» в 4.8 vs. «назначить бригадира»). Привести к одному термину во всём приложении.
- **Решение:** единый русский термин — **«бригадир»**. Английский — `foreman` (kept). Замена «подрядчик» → «бригадир» во всех ARB-файлах, design/* HTML, документации. Полнотекстовый grep по UI-строкам перед релизом.

### 10.13 Audit-log в ленту
- **Замеченный нюанс**: заказчик хочет, чтобы в ленте проекта фиксировались все события (включая действия представителя).
- **Решение:** все доменные события (через outbox в `feed_events`) попадают в публичную ленту проекта. Действие представителя — отдельная категория в feed (`actor_role: representative`), отображается с пометкой «Иванов И. (представитель Сидорова С.)». В audit-log — фактический `actorId`. Никакой фильтрации по «скрыть от представителя» не делаем.
